## Infrastructure

`foundation.cloudformation.json` is generated by:

```sh
node scripts/backup/recording-backup-template.mjs --write-template
```

It requires the verified OpenFolk AWS account ID and an owner-approved alert email.
Rules refuse a different account or a region other than London (`eu-west-2`).
The tenant parameter is pinned to the authorised Drummonds tenant. The bucket has
blocked public access, disabled ACLs, SSE-S3 encryption, versioning and 30-day
Object Lock governance retention. Stack deletion/replacement retains the bucket
and its protection policy. There is no expiration rule or deletion mirroring.
Object Lock cannot be disabled after bucket creation; governance administrators
can bypass retention, so that authority must remain separate from the runner.

The bucket policy requires TLS, explicit SSE-S3 on uploads and create-only
conditional object writes. The writer policy allows only Drummonds-prefix
creation/readback plus bucket inspection, and explicitly denies destructive and
retention-changing actions. The restore policy permits only inspection/readback.
These are **unattached managed policies**, not new users, keys or access grants.
Before use, bind each to its separately reviewed identity. Do not attach them to
an existing broadly privileged application identity.

The US$5 monthly alert is **AWS account-wide**, useful for the new dedicated
account before cost-allocation tags are activated. It is not a hard cap and does
not include Supabase egress or existing non-AWS bills. Select the actual recipient
before creating the stack. A future shared AWS account needs reviewed cost
allocation for subsystem reporting. There is no Lambda, schedule, secret, public
endpoint or source credential in this foundation stack.

Validation uses `cfn-lint` against official resource specifications; local syntax
validation is not AWS IAM simulation or proof of effective cloud configuration.
Prepare a CloudFormation change set in the verified account/region, inspect its
exact resources, then execute within the approved scope. After creation, read
back the actual policies, encryption, versioning, retention, region and public

## Copy, inventory completion and isolated restore

`scripts/backup/recording-backup-core.mjs` implements the byte-copy protocol through
injected source, S3 and durable-journal ports. The S3 destination and durable journal now have an official AWS SDK implementation
(`recording-backup-s3.mjs`); the source port is implemented in `recording-backup-source.mjs`. Live service
acceptance has not occurred. All ports must enforce the approved account/tenant/project,
TLS, bounded requests/timeouts and private create-only storage; they cannot be
populated with browser-supplied URLs, tokens or arbitrary source paths.

`backupRecording` checks the bound destination and authoritative source metadata,
streams one recording into a new private temporary file, computes SHA-256 and
rechecks the source revision. It uploads to a deterministic object key with
`If-None-Match: *`, SSE-S3 and a SHA-256 checksum, then downloads the exact returned
S3 version to verify its bytes. It checks version identity, size, encryption and
retention before recording a durable private receipt. Lost acknowledgements stop
that attempt; a later call discovers/verifies the prior object or receipt instead
of blindly overwriting. Temporary source bytes are removed on success/failure.

Each source identity includes project, tenant, storage object ID, original key,
source revision, expected size and recording references. The source adapter must
build that revision from authoritative immutable/version metadata and detect
changes around reads. ETags are not assumed to be SHA-256. Changed files remain
unconfirmed for that inventory and must be reconciled into a subsequent run.
Unreferenced and zero-byte objects are retained, without inventing playable audio.
The current per-object limit is 256 MiB; larger files fail explicitly and require
an approved bounded multipart path rather than silent omission.

`finalizeRecordingInventory` requires a complete authorised listing and a verified
receipt for **every** listed object, then rechecks the source identities before
saving a create-only manifest. Duplicate identities/keys, missing receipts,
corrupt versions or changed sources cannot become complete inventory coverage.
It handles at most 10,000 objects and reports `verified_inventory_only` and
`non_atomic`: it is not a transactionally consistent database/file snapshot.
Recovery of an already saved manifest verifies its original retained versions
and preserves its original time/scope even if sources later change or disappear.
It must never be presented as proof of current source coverage.

`restoreRecording` uses the manifest's exact S3 version and creates a new isolated
private directory (0700) and file (0600). It verifies the full byte digest and
returns original recording references. It never writes into a production path or
calls the source provider. Returned paths and manifests are private runtime data;
the restore operator must remove the temporary directory after inspection.
Playback remains `not_verified` until a real audio check is performed.

Manifests/receipts must be encrypted in the private backup destination, never Git.
Use ignored `.verification-results` only for private local journals when needed.
Public operational reports contain aggregate counts/times and safe error codes,
never audio, signed URLs, paths, credentials or customer identities.

## AWS SDK destination and encrypted journals

The isolated `scripts/backup` package pins the official AWS SDK and has its own
lockfile; the frontend dependency graph is unchanged. Construct `createRecordingS3`
with the approved context and a server-side credentials-provider function.
Construction performs no AWS calls. No default credential export, environment
secret, access key, browser token or access grant is created by this module.

Before object work it checks the STS account, London bucket location, all four
public-access blocks, enforced bucket ownership, AES256 encryption, versioning,
30-day governance retention and the required bucket-policy deny conditions.
Inspection expires after 60 seconds; every S3 request includes ExpectedBucketOwner.
The endpoint is fixed to AWS London, region redirects are disabled, SDK retries
are disabled, and requests/stream consumption have bounded deadlines. SDK logs
are suppressed in favour of safe error codes. Effective IAM-policy acceptance
still requires actual cloud tests under the eventual writer/restore identities.

Object absence is checked using `ListObjectsV2` with the exact key prefix and
`MaxKeys: 1`, compatible with tenant-prefix listing permission. HEAD alone can
return 403 for missing objects when bucket listing is restricted. Permission
failures, redirects and uncertain responses stop the operation. Once present,
HEAD/GET and post-upload verification use exact version IDs; bytes are still
independently hashed by the copy core.

Receipts and manifests use private encrypted, retained, conditional-write JSON
objects inside the same tenant prefix. JSON reads are capped at 32 MiB and checked
against their stored SHA-256 before parsing. An uncertain write is recovered by
a later invocation, never blindly retried. No deletion or retention-change
operation exists in this adapter. Source inventory persistence, scheduled runtime,
alert integration and isolated database/audio acceptance are still outstanding.

Eight SDK transport tests use the actual AWS signing/serialization/parsing stack
with a synthetic HTTP handler. The combined suite has 19 passing tests. It covers
copy → encrypted receipt → whole-inventory manifest → isolated restore, response
loss, incorrect destination configuration, denied listing, version rejection and
corrupt journals. No network request reaches AWS in these tests.

References: [HEAD permissions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html),
[bounded listing](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html),
[versioned reads](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html),
[official SDK](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/Package/-aws-sdk-client-s3/Class/S3Client).

## Supabase source and reconciliation

`recording-backup-source.mjs` uses the fixed project HTTPS origin, the private
`phone-recordings` bucket and the exact tenant prefix. It accepts an existing
authorised credentials provider only; it does not create access. Run it inside
the trusted ServiceOS/server or approved local environment. Never put a broad
source service credential into the AWS account, backup objects or journals.
Any new access grant or scheduled production deployment requires its applicable
approval; a bounded metadata-only probe reuses existing access without changing it.

Inventory begins at the tenant root and recursively lists every folder, including
folders with no recording-row references. It continues short pages until an empty
page, rejects duplicate IDs/keys/pages, and compares two full listings and two
keyset recording-reference passes. Each object must also agree with the Storage
Info API's ID, key, size, ETag and update time. The source revision includes the
provider version. Object limits are 10,000 entries and 256 MiB per file; reference
and folder limits are 10,000 each and depth 32. Exceeding a bound fails explicitly.

Each read rechecks revision and row links, requests the source with If-Match, and
validates response ETag, full content length and streamed byte count. Redirects,
partial content, encoded bodies, changed data, unsupported metadata, errors and
exhausted request budgets cannot count as complete capture. Identity/private-bucket
checks cache for at most a minute. Metadata responses are bounded at 8 MiB/30 seconds,
and byte requests at 120 seconds. Error output never includes paths or credentials.

The private reconciliation result preserves missing object references and counts
null pointers and unreferenced objects. Missing audio remains missing; zero-byte
objects remain zero bytes. Persist this report with the private inventory in the
runner before transfer; this persistence and runner are still to be completed.
Matching listings are a non-atomic observation, not a database recovery point.

Nine source tests include the entire source adapter → official AWS SDK → encrypted
receipts → complete manifest → isolated restore path, using synthetic transports.
The combined suite passes 28 tests. The read-only probe command below additionally
verified one real object's metadata against database and Storage API: three
management reads and eight source requests, no audio download or AWS request.
That proves this metadata contract for one sample, not complete live coverage.

```sh
node scripts/backup/verify-recording-source.mjs --drummonds-metadata-only
```

[authenticated downloads](https://supabase.com/docs/guides/storage/serving/downloads),
[Info response contract](https://github.com/supabase/storage/blob/master/src/storage/renderer/info.ts).

## Scoped access proposal — prepared, not executed

`access.cloudformation.json` creates **two machine IAM users** in the verified
OpenFolk account: Writer and Restore. Each receives its corresponding existing
foundation policy, also used as its permissions boundary. No login profile,
console password, administrator policy, group membership, source credential,
scheduler or key is included in this template. The account/region rules pin the
reviewed account and London deployment. AWS-generated names avoid collisions.

Writer can inspect the one backup bucket and create/read/verify objects under the
Drummonds prefix. Restore can inspect and read that prefix only. Neither can delete
backup data, bypass retention, change bucket protections or manage IAM. The
boundary restricts identity-policy permissions; it is not a claim that an AWS
administrator cannot later change account or resource policies.

CloudFormation change set `recording-scoped-access-20261011` on stack
`openfolk-drummonds-recording-access` is CREATE_COMPLETE / AVAILABLE, with exactly
these two Add actions. Schema lint and AWS deployment validation pass. Both the
editor and the independently reloaded saved template exactly match the local JSON.
It has **not been executed**; existing foundation policies remain unattached.

The requested activation also covers creating one programmatic key per machine
identity and storing each in this Mac's login Keychain, under separate services
`OpenFolk.ServiceOS.RecordingBackup.Writer` and
`OpenFolk.ServiceOS.RecordingBackup.Restore`, with the verified AWS account ID as
Keychain account. Keys must never be printed, committed, left in project files,
exported to the source provider, or used as root/admin credentials. Any transient
transfer file must be private and removed immediately after verified Keychain
storage. The restore key is loaded only for deliberate restore checks, not the
copy scheduler. Production deployment/credential transfer remains a separate gate.

These are long-lived programmatic keys for the initial trusted local copy/restore
runner, not expiring sessions. A key compromise would expose the permitted backup
prefix. Record creation/last-use metadata, rotate within 90 days and revoke promptly
when this runtime is retired. Prefer workload roles/temporary credentials when
moving to a hosted runner; these users grant no deployment permission. An operator
can disable either key to stop access without deleting retained recordings.
[AWS access-key guidance](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html).

Creating these new identities and keys grants new security-sensitive access, so
browser action-time confirmation is required before execution/provisioning.
The existing approved recording-copy destination and scope are unchanged.
