# Reliable job-first Home reads · 21 October 2026

The signed-in MD Home has timed out on both saved-job totals and confirmed-customer groups. Its separate paged job reader works, but both Home RPCs repeatedly scan retained Commusoft history and leave the screen showing dated last-good results. A successful warm read is not a durable fix. This release gives both existing audited Home readers one transactional current-source projection; it does not add a provider request or publish a score.

## Exact scope

- LIVE project: `tgbnakbxwcqjeimygroz`.
- Stage 1: `20261113000000_new_dawn_commusoft_current_job_source.sql`, SHA-256 `d1a2c9e754b285d6a8360427d5e75db1d7359a969871b53fb09365981e1ef46c`. It creates a private tenant/connection/external-ID keyed projection and an observation-insert trigger. Each new retained page updates this projection in the same transaction. The immutable page, version and observation rows remain the source of truth.
- Stage 2: `20261113010000_new_dawn_open_job_summary_current_source.sql`, SHA-256 `2c19c89b0c24cd896655702c1095614400db7d36c4ca14be10a437815ae7fa49`. It backfills the projection from retained observations, then changes only the latest-source selection inside `new_dawn_open_job_status_summary` and `new_dawn_customer_blockers`. Both RPCs retain their actor, tenant, flag, exact-link/site checks, audit, output and grant contracts.
- An equal-time tie between different source versions is marked ambiguous and withheld from both readers. A later unambiguous version resolves that hold, but a customer group still needs an exact current job link. The projection exposes no direct table grants, including to authenticated users and the service role; only the existing audited RPCs can return their scoped results.
- No customer/site/job link, source row, provider setting, client flag, login, score or accounting record changes. The frontend still clearly dates a prior successful read if the new read fails.

## Guard and rollback

The release is two separate transactions. Each inserts its exact SQL source into the migration ledger under a lock. Stage 2 runs only after independent readback of Stage 1. Both stages stop if either function hash/grant, projection/trigger state or ledger differs. A lost acknowledgement is resolved by readback; never replay a write blindly. The status-summary function changes from SHA-256 `1a373342368cc703a09860bc6162c0a98a8116cebd104719d212449fb9603f9a` to `9219b20578e4213f927785ffd4c0714066cdb5972997b7b02e9024ef0fff4e23`. The customer-group function changes from `edc63a68703186905bbd7a61a791629c843b14a4ebdefe3b9660260f51e17e55` to `a2f5916d204014e3affced8136308a74e67d6c0d42ea7856cdf27d7276f813c0`.

The exact rollback at `supabase/release/new-dawn-current-job-source/rollback.sql` checks both candidate hashes, restores both original audited definitions, then removes only the derived trigger, function and table in one transaction. If Stage 1 commits but Stage 2 does not, `stage-1-only-rollback.sql` removes only that unused projection after checking both readers remain on their baseline hashes. Source history is untouched. The migration ledger remains as release history and a later reinstall would require a separately reviewed version.
