# LEARN daily saved-input ledger

This client LEARN section shows the number of records first saved today and the running retained total, as of one database read. “Today” is the `Europe/London` calendar day. It is a capture ledger, not a statement that provider history is complete or that an email/call happened today. A historical email imported today appears in today's saved count. A revised Commusoft job does not add another job identity.

The seven rows are saved calls (`phone_calls`), recording metadata (`phone_recordings`), email messages (`email_messages`), public Slack channel messages with current-version visibility proof (`slack_messages`), and distinct saved Commusoft job, customer-property and workaddress-property source IDs (`learn_business_input_versions`). Slack tombstones/private or unproved messages are excluded. Commusoft property IDs whose saved versions disagree about customer/site type are excluded from those typed rows; no identity or canonical link is inferred.

The “newest saved Commusoft job” uses Commusoft's source-created timestamp and numeric source ID for ordering, matching the independent provider-freshness reader. It shows when that job identity was first retained; a later revision of an older job cannot displace it. Jobs lacking a valid source-created timestamp or numeric source ID remain in the totals but are not eligible for this newest-job comparison. The source ID is still displayed as a string. The separately authorised provider check has its own timestamp; if saved jobs advance after that check, the comparison explicitly needs refreshing instead of claiming to be current.

The migration adds only an aggregate RPC. It seeds no flags or schedules. Client display requires `new_dawn.learn_daily_stats=true`, an active same-tenant owner/admin login, no platform authority and no View-As. OpenFolk preview requires `new_dawn.learn_daily_stats.operator_preview=true`, platform admin authority, an explicit reason and an audit row. The existing LEARN screen remains unchanged while both flags are absent. Heidi's login is not altered.

Before enabling the client flag: install the migration through the normal reviewed release; check the exact LIVE tenant and signed-in owner/admin response; compare all seven numbers to focused read-only database counts; review a mobile viewport; verify the same-tenant client and operator audit entries; verify foreign-tenant, staff, disabled-login and View-As reads fail. Then enable the client flag only for the reviewed tenant. Switch it off to roll back the UI; retain the audit and function until callers have been checked.

Local validation: `node --test src/lib/new-dawn-learn-daily-stats.test.ts`; TypeScript and production build; then, in a disposable PostgreSQL 17 database, apply `scripts/verify/new-dawn-learn-daily-stats-bootstrap.sql`, this migration, and `scripts/verify/new-dawn-learn-daily-stats-synthetic.sql`. The synthetic fixture tests two-tenant separation, public Slack proof, a revised job counted once, preserved leading zeroes, operator audit, View-As refusal and default-off behavior.

The split RPC is in `20261110140000_new_dawn_learn_daily_stats_split.sql`, and its own fixture is `scripts/verify/new-dawn-learn-daily-stats-part-synthetic.sql`. The newest-job correction is in `20261110160000_new_dawn_learn_newest_saved_job.sql`; after the prior fixtures, run `scripts/verify/new-dawn-learn-newest-job-synthetic.sql` to prove that a later committed revision of an older job does not replace the newest source job. This is a retained-source comparison, not a provider completeness claim or a signed-in UI acceptance receipt.
