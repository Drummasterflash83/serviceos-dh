## 2. The mission the team must preserve

OpenFolk is an operational-improvement company. ServiceOS is its expression for service businesses; ProductOS is the future expression for product and commerce businesses. They share one underlying intelligence platform. OpenFolk supplies managed intelligence and human judgement; OpenFolkOS is where operators supervise, govern and improve the service and its development.

The target operational loop is:

**Authorised evidence → understanding → recommendation → decision → appropriate approval → execution → verified outcome → learning.**

The improvement loop identifies recurring causes, simplifies or removes avoidable work, and improves policy, configuration or common capabilities. More agent activity is not evidence of business improvement.

| Vision commitment recovered from the conversation | Binding build consequence | Evidence of fulfilment |
|---|---|---|
| Learn how the business actually operates | Reuse authorised source ingestion, identity and relationship foundations | Trace an operational decision back to actual source evidence |
| Improve sustainable net profit without sacrificing quality, safety or commitments | Connect backlog items to cash, cost, capacity, margin, renewals or operational quality | Outcome measure with baseline, owner and observation period |
| AI owns routine work within earned authority | Explicit policies and audited execution, with escalation where authority is missing | Allowed action succeeds; denied and stale approvals do not execute |
| OpenFolk absorbs machine uncertainty | Send evidence conflicts and missing policy to OpenFolk review | A conflict is resolved without unnecessarily burdening the client |
| Clients retain business judgement and consequential authority | Route judgement and commercial approval to the client's authorised person | Correct approval identity and scope recorded |
| Small surfaces, deep capability | Extend current screens and components; remove duplication | Before/after visual evidence and a coherent user journey |
| One platform, repeatable delivery | Tenant configuration rather than customer-specific forks | A second synthetic tenant works without bespoke code |
| Universal, industry and company learning remain distinct | Keep company context private; govern promotion of generalised lessons | Cross-tenant negative tests and a reviewed learning example |
| Remove founder/operator dependency | Durable ownership, runbooks, checkpoints and evidence | A second authorised operator can continue a workflow |

The ambitions of roughly twenty companies per capable operator, and eventually hundreds with AI support, are design ambitions from the prior synthesis. They are not V1 staffing promises.

### Architecture and design constitution

1. Improve the existing product. Preserve the prior plan's TanStack Start/Router and React foundation, Vercel frontend deployment and separately deployed Supabase backend, subject to current-repository verification.
2. No framework migration, new design system, replacement dashboard, speculative navigation expansion or second intelligence engine as incidental task work.
3. Extend the existing operator-gated `/openfolk` workspace. Preserve tenant navigation, audit, version checks and View-As restrictions.
4. Preserve the shared wordmark, brand guard, typography, spacing, components and interaction patterns. Experience records the current design baseline before changes.
5. One purpose per screen; no duplicated actions or intelligence. Show truthful loading, empty, stale, denied and error states. Never present fixture data as production data.
6. Reuse existing identity, business graph, decisions, authority, execution, outcome and learning records. Map an existing capability before adding another.
7. Protect ProductOS through shared interfaces, governed configuration and tenant isolation. Do not build commerce, stock or fulfilment surfaces while the ServiceOS V1 path remains unfinished.
8. Treat the separately owned Emma launch/routing configuration as out of scope. Reliability may investigate related symptoms but cannot change routing, telephony settings or launch controls without a specific authorised task.
9. Any structural exception requires a short decision record: existing limitation, smallest viable change, alternatives, migration/recovery impact and Chris's decision. Routine implementation choices within these boundaries remain autonomous.

## 4. Authority, permissions and approval boundaries

A prompt is an operating instruction, not a security boundary. Enforce permissions through actual repository protection, environment separation, credential scope and provider controls. If a shared account cannot isolate a sensitive permission by role, withhold that permission from the coding environment and use a human-operated release step.

### Authority levels

| Level | Allowed work | Activation |
|---|---|---|
| L0 — baseline | Read approved source documents, code and sanitised metadata; prepare local plans | Initial setup |
| L1 — activation exercise | One harmless non-production change, draft PR, isolated tests and separate review | Chris starts the exercise in section 14 |
| L2 — bounded delivery | Approved backlog implementation, isolated branches, authorised test resources, draft PRs and internal engineering evidence | After activation PASS and standing authorisation |
| L3 — consequential action | Exact production release, live schema/auth change, external communication or financial/provider action | Specific human approval for each action or an explicit narrowly scoped standing policy |

No role can grant itself a higher level. Chris may delegate business decisions only within authority he actually holds; a client-authorised decision-maker remains necessary for client commitments.

| Action | Default owner | Rule |
|---|---|---|
| Read code, approved docs and sanitised diagnostics | All roles | Within task scope and existing access |
| Create engineering issues and update task evidence | Conductor; assigned roles for their records | L2 standing authority must include this repository and internal audience |
| Edit implementation code | Reliability, Core, Control, Experience | Assigned branch and paths only; non-production resources only |

## 6. Task states and transition ownership

Keep engineering delivery state separate from provider execution state. Provider values such as running, awaiting input, finished, failed, cancelled or unknown are observations; they do not by themselves establish acceptance.

| Engineering state | Entry condition | Who advances it |
|---|---|---|
| BACKLOG | Outcome identified; not dispatchable | Conductor |
| READY | Contract complete; dependencies accepted; permissions, budget and ownership available | Conductor |
| IN_PROGRESS | One owner has accepted the contract; run ID and branch recorded | Conductor records accepted start |
| REVIEW | Builder submits candidate SHA and complete handoff | Conductor validates packet; Assurance starts review |
| CHANGES_REQUIRED | Independent review identifies unmet criteria | Assurance verdict; Conductor returns work to owner |
| INTEGRATION_READY | Assurance passes the candidate; no unresolved blocking findings | Conductor accepts review |
| INTEGRATING | Release owns the integration slot | Release, under Conductor dispatch |
| RELEASE_READY | Exact integrated candidate passes checks; manifest and recovery ready | Release proposes; Assurance confirms |
| AWAITING_APPROVAL | Concrete consequential action needs human decision | Conductor requests |
| DEPLOYING | Valid approval and environment preflight confirmed | Release/authorised human |
| VERIFYING | Provider reports deployment; product checks remain | Release and Assurance |
| DONE | Applicable definition of done and outcome verification accepted | Conductor closes with evidence |
| BLOCKED | Named external dependency, missing access, exhausted quota or unknown critical state | Conductor; resume to READY after resolution |
| PAUSED | Explicit pause or safety/spend stop; checkpoint saved | Conductor; resume only after authority is restored |
| CANCELLED | Work withdrawn; running executions reconciled and artifacts preserved | Conductor |

For a documentation-only task, the contract may define DONE after independent acceptance without a deployment. For product work, a merged PR is not DONE until the required environment and outcome checks pass. A release failure returns affected work to BLOCKED or CHANGES_REQUIRED and opens a recovery/incident record.

## 7. Branching, merge and anti-collision rules

1. At baseline, identify the remote default branch, production-connected branch, active human/agent work, uncommitted changes, open PRs and deployment triggers. Never assume an old checkout is current.
2. Use one isolated checkout/environment and one branch per task: `of/<issue-id>/<role>/<short-scope>`. Branch from the recorded current base; do not alter someone else's working tree.
3. Use draft PRs for work in progress. Link the issue, contract, gates and evidence. Keep changes small enough for independent review.
4. Release owns `of/integration/<release-id>` as a proposed naming convention. Verify that this branch targets only isolated preview resources before pushing or invoking CI.
5. Serialise integration. Bring accepted task commits into the integration branch using merge commits; rerun the relevant combined checks. Preserve the reviewed individual commits.
6. Do not force-push or rewrite already-pushed history. Preserve the Lovable history rule. Update branches with merge commits. Do not squash or rebase published commits as a convenience.
7. Treat a merge to `main` as a production release until the current deployment configuration proves otherwise. No auto-merge to production-connected branches.
8. Require all actual repository checks, independent Assurance evidence and an authorised human release decision. Do not disable a failing check or silently lower coverage to pass.
9. A review performed by an AI under the author's GitHub account is not an independent GitHub-user approval. Use a real eligible reviewer where branch protection requires one. If unavailable, stop at RELEASE_READY; never bypass the rule.
10. Freeze the approved candidate and manifest. If the base, code or configuration changes, rebuild the integrated candidate and repeat affected checks. Record the relationship between the tested tree and final merge commit; do not label an untested commit as tested.
11. Frontend and Supabase changes need an explicit compatible rollout order. Prefer additive, backwards-compatible changes; destructive migration and data restoration require specific approval and a tested plan.

### Ownership ledger

Conductor is the sole allocator. Reuse an existing task/ownership mechanism; do not create a new platform to manage locks. A ledger entry records resource/path scope, issue, role, run ID, branch, start, last checkpoint and release condition.

| Shared resource | Default coordinating owner | Rule |
|---|---|---|
| Database migrations and generated database types | Core, sequenced by Release | One writer; agree ordering; regenerate from the accepted schema |
| Authentication, tenant policies, roles and authority | Core + independent Assurance review | Reserved scope; specific approval; no simultaneous unrelated edits |
| Shared UI shell, navigation, tokens and wordmark | Experience | Control requests shared changes through one owner |
| Dependency manifests and lockfiles | Release | One owner; justified dependencies only; no opportunistic upgrades |
| CI, Vercel/Supabase configuration and secrets | Release | Serial changes; production credentials outside builder environments |
| Connector cursors, replay queues and test tenant data | Reliability | Isolated fixtures/tenants; no concurrent destructive replay |
| Engineering status projection | Control | Canonical IDs, deduplication and stale-state handling |

A timed-out task does not automatically free its resources. Conductor first checks provider state, stops or obtains a checkpoint from the old owner, preserves its work, and records transfer. If state is unknown, keep the lock and investigate. Every role rechecks ownership before shared mutations.

All other tools, human developers and Lovable activity count as writers. An unexpected commit or overlapping change triggers reconciliation, not overwriting. One task never resolves a collision by silently discarding another's work.
